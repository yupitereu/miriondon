# Git 및 커밋 규칙

이 문서는 `miriondon` 저장소에서 Git 작업과 커밋을 수행할 때 적용하는 기준입니다. PR 생성 시에는 [`.ai/skills/create-pr/SKILL.md`](skills/create-pr/SKILL.md)를 함께 적용합니다.

## 1. 커밋 메시지 컨벤션

Conventional Commits 형식을 사용하며, 제목과 본문은 **한국어**를 기본으로 작성합니다.

```text
<type>(<scope>): <subject>

<body>
```

### 1.1 Type

| Type       | 설명                                                  |
| ---------- | ----------------------------------------------------- |
| `feat`     | 새로운 기능 추가                                      |
| `fix`      | 버그 수정                                             |
| `refactor` | 동작 변경 없는 코드 리팩터링                          |
| `style`    | 코드 의미에 영향을 주지 않는 포맷팅, 세미콜론 등 수정 |
| `docs`     | 문서 및 AI 규칙 추가·수정                             |
| `test`     | 테스트 코드 추가·수정                                 |
| `build`    | 빌드 설정, 패키지 매니저, 의존성 변경                 |
| `chore`    | 기타 설정 및 유지보수 작업                            |

### 1.2 Scope (선택)

변경 범위를 명확히 드러낼 필요가 있을 때 소문자로 작성하며, 전체 영역에 걸친 변경이거나 범위가 자명하면 생략할 수 있습니다.

- 주요 예시: `client`, `server`, `ui`, `config`, `ai`, 또는 세부 기능/모듈명(`layout`, `security` 등)

### 1.3 Subject (제목) 및 Body (본문)

- `[필수]` 제목은 한국어 명사구 또는 간결한 서술형으로 작성하고 마침표(`.`)로 끝내지 않습니다. (예: `feat(ui): 버튼 컴포넌트 추가`)
- `[필수]` 제목은 50자 이내를 권장하며 변경의 핵심 목적을 드러냅니다.
- `[권장]` 단일 커밋으로 의도가 충분하면 본문을 생략하고, 배경·제약·주요 변경 이유를 설명해야 할 때만 제목과 빈 줄 하나로 구분해 본문을 작성합니다.

## 2. 스테이징과 커밋 원칙

- `[필수]` 커밋 전 `git status`와 `git diff`로 작업 트리를 확인하고, 요청 범위와 무관한 변경 파일이나 임시 파일을 함께 스테이징하지 않습니다.
- `[필수]` 환경 변수(`.env*`), 인증 정보, 개인 금융 데이터, 에디터/OS 생성 파일(`.DS_Store`, `.idea/`), 로컬 패키지 캐시(`.pnpm-store/`)는 절대 커밋하지 않습니다.
- `[필수]` 논리적으로 독립된 작업은 하나의 커밋에 섞지 않고 분리합니다.
- `[검증]` 커밋 전 `git diff --cached --check`로 공백 오류나 충돌 마커가 없는지 확인합니다.

## 3. 브랜치 네이밍 컨벤션

`main`, `dev` 등 코어 브랜치를 제외한 작업 브랜치는 `<type>/<short-description>` 형식을 사용합니다.

```text
<type>/<short-description>
```

- `[필수]` 브랜치 이름은 **영문 소문자, 숫자, 하이픈(`-`), 슬래시(`/`)**만 사용하여 `kebab-case`로 작성합니다. (예: `feat/mvp-setup`, `fix/login-redirect`, `docs/ai-rules`)
- `[필수]` `<type>`은 커밋 메시지 컨벤션의 Type(`feat`, `fix`, `refactor`, `docs`, `test`, `build`, `chore` 등)과 동일하게 맞추며, `feature/*` 대신 `feat/*`를 사용합니다.
- `[필수]` `<short-description>`은 수행할 작업을 한눈에 식별할 수 있도록 간결하고 명확한 영문 키워드로 작성합니다.

## 4. 커밋 이력 정리 (Rebase & Squash)

- `[권장]` 동일한 파일·영역의 수정이 **연속되거나**(예: `A 수정 커밋` → `A 추가 수정 커밋`), **다른 커밋을 사이에 두고 나뉘어 있으면서**(예: `A 수정 커밋` → `B 수정 커밋` → `A 추가 수정 커밋`) 맥락이 사실상 동일하다면 `amend` 또는 `rebase`와 `squash`(혹은 `fixup`)로 병합해 클린 커밋 이력을 유지합니다.
- `[필수]` 이력 정리가 허용되는 범위는 다음과 같습니다.
  - 아직 원격 브랜치에 푸시되지 않은 로컬 커밋
  - 원격에 푸시되었더라도 `main`, `dev` 등 코어 브랜치가 아닌 **작업 브랜치**(예: `feat/*`, `fix/*` 등)의 커밋 (필요 시 `--force-with-lease` 사용)
- `[필수]` `main`, `dev` 등 **코어 브랜치에 이미 푸시되었거나 코어 브랜치에 병합(merge)된 커밋**은 절대 `amend`, `rebase`, `squash`, `reset --hard`, `push --force`하지 않습니다.
- `[필수]` 이력 정리는 **충돌(conflict)이 발생하지 않는 경우**에만 수행합니다. 리베이스 중 충돌이 발생하면 즉시 `git rebase --abort`로 원상 복구하고 개별 커밋을 유지합니다.
