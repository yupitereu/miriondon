## 2. 이 가계부를 사용하는 목적

통장에 보이는 잔액만으로 쓸 수 있는 생활비를 판단하지 않는다. 카드로 이미 사용한 돈, 앞으로 발생할 고정지출, 받을 돈을 함께 반영해 생활비를 관리한다.

특히 다음 두 가지를 기존 카드사 화면만으로 해결하기 어려워 별도 시트를 사용한다.

1. 아직 자동결제되지 않은 고정지출도 미리 생활비에서 제외한다.
2. 예정된 고정지출까지 카드 실적에 반영해, 혜택 기준에 부족한 금액을 확인하고 평소 사용할 카드를 선택한다.

결제 계좌로 넘긴 돈은 실제로 아직 보유하고 있어도 이미 나갈 돈으로 보고, 더 쓸 수 있는 생활비에서 제외한다. 반면 다른 사람이 부담할 금액은 아직 돌려받지 않아도 받을 돈으로 반영한다. 따라서 이 사용자의 생활비는 현재 현금만을 기준으로 한 보수적인 잔액과 같지 않다.

## 4. 지불상태와 실제 정리 순서

### 현재 사용 방식

| 결제 방식     | J열이 Y인 의미                                 |
| ------------- | ---------------------------------------------- |
| 신용카드      | 생활비에서 결제 계좌로 필요한 준비금을 옮겨 둠 |
| 현금          | 실제 현금을 지불함                             |
| 직접 계좌이체 | 상대방에게 실제 송금함                         |

Y의 공통 의미는 해당 지출을 생활비에서 이미 처리했다는 것이다. 카드의 경우 준비금 확보와 카드대금의 실제 출금은 서로 다른 사건이다.

평소 정리 과정은 다음과 같다.

1. 지출 기록을 모두 작성한다. 고정지출과 할부 예정분도 포함한다.
2. 계좌별 이체 필요액을 확인하고 한 번에 이체한다.
3. 해당 거래들의 지불상태를 Y로 바꾼다. 평소에는 기록을 마친 전체 지출 항목을 Y로 변경한다.
4. 조정금액을 반영해 이체했다면 조정금액을 0원으로 돌린다.
5. 실제 통장 잔액을 확인하고 생활비 잔액오차가 0인지 점검한다.

현재는 여러 거래에 대한 이체를 한 번에 하더라도 거래 행의 상태를 직접 바꿔야 한다.

### 분석상 주의점

- 준비금을 옮긴 뒤 실제 카드대금이 출금될 때 생활비를 다시 차감하면 안 된다.
- 현금·직접 이체의 지급 완료와 신용카드의 준비 완료를 같은 사건으로 저장하면 안 된다.
- 거래 일부를 선택해 해당 거래만 Y로 처리할 수 있다. 서비스는 거래 단위 선택·전체 처리를 지원하고 한 거래 금액 일부만 준비하는 기능은 제외한다.

## 5. 실제 잔액, 예정 입출금과 대조

### 현재 사용 방식

- 현재보유금액에는 은행 앱에서 확인한 실제 잔액을 그대로 입력한다.
- 아직 결제 계좌로 옮기지 않은 준비금 등은 지출예정금액에 반영한다.
- 돌려받을 돈은 수입예정금액에 반영한다.
- 돈을 실제로 받으면 수입예정금액을 줄이고 현재보유금액을 늘린다. 받을 돈과 받은 돈을 동시에 남기지 않는다.
- 자산현황에서 예정 입출금을 반영한 생활비와 월별 예산상 생활비의 차이를 확인한다.
- 잔액오차가 0이면 정리가 끝났다고 판단한다. 차이가 나면 지출 기록의 오류·누락을 직접 찾는다.

### 자산현황 탭의 등록 정보·집계 구조

- A:G는 구분·소유자·상품유형·용도·금융사·계좌(증권)번호·상품명이다.
- H:K는 현재보유금액·수입예정금액·지출예정금액·합계다. 개별 항목의 기본 계산은 `현재 보유 + 예정 수입 - 예정 지출`이다. 일부 수동 입력·별도 수식도 있어 모든 행이 동일하게 동작한다고 단정하지 않는다.
- 생활비·결제용 계좌와 현금 외에 저축·투자·연금·보험·부동산·대출 등의 항목도 기록돼 있다.
- 소유자별 소계, 구분별 합계와 전체 총계가 있다. 생활비 잔액오차는 전체 자산 총계가 아니라 생활비 계산 대상 항목과 월별 예산 잔액을 대조한다.
- 결제 계좌의 예정 유입에는 월별 준비금·이체 계산을 참조하는 항목이 있다. 서비스에서는 외부 수입과 내부 준비금 이동을 구분해 전체 자금을 부풀리지 않아야 한다.

자산현황은 자산별 등록 정보·현재 및 예정 금액·소유자별 현황을 한곳에서 조회하고, 생활비 잔액을 대조하는 역할을 한다. MVP는 저축·투자·연금·부동산·대출의 등록·수동 금액 갱신·합계 조회를 포함하고 시세·수익률·이자·상환 자동 계산은 제외한다.

월별 예산 표의 계산 관계는 다음과 같다.

```text
W열 이월금 = 전월 같은 분류의 Z열 최종 잔액
X열 지출합계 = 같은 분류 중 통계제외가 N인 실거래액 합계
Y열 금월 잔액 = V열 예산 - X열 지출합계
Z열 최종 잔액 = V열 예산 + W열 이월금 - X열 지출합계
```

전월에 남은 금액과 초과 지출은 모두 같은 분류의 다음 달로 이어진다.

### 서비스 요구

실제 잔액 입력·잔액 차이·계산 근거를 제공한다. 잔액 차이에 따른 저장 제한이나 완료·미완료 상태는 두지 않는다. 마지막 일치 시점 이후의 변경으로 원인을 추적하는 고급 기능은 MVP에서 제외한다. 보안·권한에 필요한 내부 이력은 유지한다.

## 6. 통계제외, 대신 결제와 정산

### 기존 용돈 처리

용돈을 지급할 때 이미 생활비 지출로 반영한다. 예를 들어 용돈을 20만 원 지급한 뒤 그 안에서 개인 지출을 했다면 개별 사용을 생활비 지출에 다시 합산하지 않는다.

생활비 쪽에서 결제되는 수단으로 개인 지출을 했다면 통계제외를 Y로 두고, 해당 금액을 용돈계좌에서 생활비 계좌로 반환한다. 반환은 새로운 소득이 아니다.

### 기존 가족 사용분 처리

가족이 본인 명의 카드를 사용한 경우 통계제외를 Y로 두고, 비고에 정산 대상을 표시한다. 여러 사용 건을 합쳐 다음 달 초에 돌려받는다.

예시: 쓸 수 있는 생활비가 100만 원일 때 가족 사용분 10만 원을 내 돈으로 먼저 결제 계좌에 준비해 둔다. 같은 금액을 받을 돈으로 반영하므로 생활비는 100만 원으로 유지한다. 입금 시 받을 돈을 줄이고 실제 보유금을 늘린다.

- 개별 사용 기록 없이 가족 카드 합계만 별도 관리하는 기능은 MVP에서 제외한다.
- 가족 사용분도 개별 거래로 유지한다. 후속 세무 기능에서는 실제 세법상 귀속·공제 기준을 별도로 적용한다.

### 정산 요구

| 항목              | 처리 기준                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| 적용 상황         | 가족 대신 결제와 더치페이 등 내가 먼저 결제하고 돈을 돌려받는 상황                                    |
| 생활비            | 전체 결제액 중 내가 부담할 금액만 차감. 아직 못 받은 금액도 받을 돈으로 반영                          |
| 카드 준비         | 받을 돈과 별개로 전체 카드 결제 필요액을 준비                                                         |
| 입력              | '돌려받을 금액 있음' 체크 시 거래금액 전액을 기본 입력하고, 일부만 받을 때 수정                       |
| 실사용자와의 관계 | 실사용자 지정과 정산 여부는 별개. 실사용자를 바꿔도 자동으로 받을 돈을 만들지 않음                    |
| 실제 정산         | 사용자가 정산 완료금액을 직접 처리. 입금 내역으로 자동 정산하지 않음                                  |
| 여러 건·여러 입금 | 가족의 합산 입금, 더치페이 참여자들의 시차 있는 입금을 수용해야 함. 거래·사람별 배분 화면은 미정      |
| 반대 상황         | 다른 사람이 먼저 결제한 경우에는 내가 실제 송금한 뒤 지출로 기록. 별도 '보낼 돈' 기능은 추가하지 않음 |

예시: 9만 원을 결제하고 내 부담이 3만 원이면 생활비 지출은 3만 원, 받을 돈은 6만 원이다. 전액을 다른 사람이 부담하면 내 부담은 0원이다.

실사용자별 자동 정산 규칙은 제공하지 않는다. 사용자가 받을 돈을 체크하고 필요한 금액을 수정한다.

## 7. 조정금액

### 현재 사용 방식

조정금액은 이미 준비금을 이체한 뒤 거래금액이 달라졌을 때, 다음 이체에 반영할 미처리 차액이다.

| 사례                         | 거래 수정                   | 조정 처리                          |
| ---------------------------- | --------------------------- | ---------------------------------- |
| 온라인 구매 반품·취소        | 취소된 금액만큼 지출을 줄임 | 음수로 기록해 다음 이체액에서 차감 |
| 휴대폰 소액결제 등 추가 청구 | 기존 고정지출 금액을 늘림   | 양수로 기록해 다음 이체액에 추가   |

음수 조정의 남은 준비금은 결제 계좌에 두고 다음 이체에서 상계한다. 조정을 반영한 금액을 이체하면 조정금액을 0원으로 초기화한다.

현재는 거래금액 수정과 조정금액 입력을 따로 해야 한다. 서비스에서는 원거래·기존 준비 처리·미처리 차액을 연결하고 다음 이체에 반영한 차액을 소진한다. 차액 확인·상계 화면은 상세 설계 대상이다.

## 8. 고정지출과 예정 거래

### 현재 사용 방식

- 고정지출은 실제 청구 전에 예상 금액으로 미리 적는다. 이것이 현재 관리 방식의 핵심이다.
- 월말 자동결제 예정액까지 생활비에서 빼고 카드 실적에 포함해야 한다.
- 시트의 고정지출 거래일을 1일로 적은 것은 정렬 편의 때문이다. 실제 결제일이 모두 1일이라는 뜻이 아니다.
- 실제 청구금액이 예상과 다르면 기존 거래금액을 수정한다.
- 이미 준비금을 이체했다면 차액을 조정금액에 기록한다.
- 실제 결제를 확인했다는 별도 표시는 현재 하지 않는다.

### 서비스 요구

실제 예정일과 고정·변동지출을 구분한다. 파일의 실제 내역을 예정 거래와 연결해 금액을 보정하며 매 건 별도 결제 확인 버튼을 필수 절차로 두지 않는다. 모호한 연결·변경은 사용자가 확인한다.

## 9. 할부

### 현재 사용 방식

- 60만 원을 3개월 할부로 사면 매달 20만 원씩 생활비에서 차감하고 준비한다. 첫 달에 전체 원금을 생활비에서 빼지 않는다.
- 할부 시작 시 이후 두 달의 시트에도 미리 월별 납부액을 적어 둔다.
- 나누어떨어지지 않는 금액은 임시로 배분한 뒤 카드사에서 확인한 회차별 금액으로 조정한다.
- 첫 회차 납부액이 이후 회차보다 큰 사례가 있다. 회차별 실제 금액은 카드사 확정 내역을 기준으로 보정한다.
- 현재 사용하는 카드의 할부 실적은 첫 달 전체 승인액, 이후 회차 0원이다.

### 서비스 요구

월별 생활비 부담과 카드 실적 인정은 분리한다. 카드별로 할부 실적을 첫 달 전체 또는 회차별 납부액으로 인정하는 조건을 설정할 수 있어야 한다. 카드사별 반올림·잔여액 배분을 추측해 확정하는 대신 실제 회차별 금액으로 보정할 필요가 있다.

## 10. 카드 이용실적과 조건

### 현재 사용 방식

- H열 실적산정은 세금, 할인받은 거래 등 실적 제외 항목을 직접 지정하는 데 사용한다.
- 할인받은 거래의 인정 방식은 카드에 따라 거래 전체 제외, 할인금액만 제외, 전액 인정으로 달라질 수 있다는 사용 경험이 있다.
- 현재 사용 기준은 결제일과 관계없이 매월 1일~말일이다. 모든 카드사의 보편적 정책으로 검증한 것은 아니다.
- 사용 목적은 단순 실적 조회가 아니라 예정 고정지출을 포함한 부족분을 보고 사용할 카드를 고르는 것이다.

### 서비스 요구

카드 정보에 실적 인정 조건을 넣어 거래에 자동 적용할 필요가 있다. 할부 인정 방식과 할인 거래 처리, 특정 항목 제외 등을 구분해야 한다. 거래별로 매번 Y/N을 입력하는 부담을 줄이는 것이 목적이다.

예정 포함 실적과 목표 부족액은 MVP 핵심 기능이다. 카드 선택·없는 상품의 공식 자료 AI 탐색·개인용 조건을 지원하고 공용 조건은 운영자가 검수한다. 약관 상시 자동 갱신과 전체 혜택 최적화는 제외한다.

## 11. 수입과 예산 귀속

### 현재 사용 방식

- 분류별 예산에는 처음 정한 기준값이 있다. 매달 예상 실수령액과 큰 지출 계획에 따라 조정한다.
- 월별 수입내역은 예상 실수령액으로 미리 기록한다.
- 현재 사용자는 전월에 입금된 월급을 금월 수입으로 배정한다.
- 월급은 회계월이 시작하기 전에 이미 들어와 있으므로 실제 월급을 수입예정금액에 적는 일은 없다.
- 들어온 월급은 별도 통장에 보관했다가 해당 회계월에 생활비 계좌로 옮긴다.
- 아직 안 받은 수입을 수입예정금액에 잡는 원칙은 가능하지만, 이것과 현재 월급 운용 사례를 혼동하면 안 된다.

### 서비스 요구

- 수입은 급여·비급여로 나누어 건별 기록한다. 급여는 사용자 정의 지급·공제 항목과 과세·비과세를 구분한다.
- 실제 입금일·급여 귀속 연월·예산 반영월을 구분한다. 예산 반영월의 기본값은 상세 입력 설계 대상이다.
- 별도 통장 사용이나 다음 달 자금 잠금 기능을 강제하지 않는다.
- 반환금·정산금·내 계좌 간 이동을 일반 수입으로 중복 집계하지 않는다.

## 12. 결제수단 소유자와 실사용자

### 서비스 요구

- 기존 사용자 열의 목적은 결제수단 소유자 기준 집계다. 카드·계좌 등록 시 소유자를 기록하고 거래에서는 참조하면 되므로 반복 입력하지 않는다.
- 실사용자는 별도 정보로 기록한다. 소유자와 실사용자를 동일한 개념으로 취급하지 않는다.
- 실사용자가 될 사람은 미리 등록할 수 있다. 가계부 참여 구성원을 기본 포함하고, 가입하지 않은 가족·친구도 추가할 수 있다.
- 실사용자로 등록한다고 가계부 조회·참여 권한을 주지 않는다.
- 실사용자가 다른 사람이어도 선물처럼 내가 부담하는 지출일 수 있다. 실사용자 변경만으로 통계제외나 받을 돈을 자동 확정하지 않는다.

실사용자 선택의 기본값, 여러 실사용자의 표현 방식, 사람 삭제·탈퇴 후 과거 기록 표시는 추가 검토 대상이다.

## 13. 공동 관리와 공개 범위

### 서비스 요구

- 각자가 자기 카드·계좌의 공개 범위를 정한다. 공동 가계부 관리자도 비공개 상세 내역을 볼 수 없다.
- 카드·계좌별 기본 공개 설정과 거래별 예외 변경을 지원한다.
- 기본 공개 수준은 나만 보기이며, 필요할 때 합계 공유 또는 상세 공유를 선택한다.
- 거래는 기본 설정을 따르고 예외 변경은 거래 상세에서 제공한다.
- 공동생활비에 포함할지와 상세를 누구에게 보여줄지는 별개의 속성이다.
- 기본 공개 변경 시 이후 거래만 또는 기존 거래에도 적용할지 선택한다. 명시적인 거래별 공개 예외가 우선한다.
- 새 구성원은 과거 공유 기록도 볼 수 있고 탈퇴자는 접근이 종료된다. 공동 기록·합계는 유지한다.
- 소유자는 한 명이고 관리자는 여러 명 지정할 수 있다. 상세 공유 거래는 구성원 모두 수정하며 설정은 별도 권한을 따른다.

## 17. 한 결제의 여러 지출 분류와 카드사 할인

### 현재 불편

마트 등에서 한 번 결제해도 실제 구매 내용은 여러 지출 분류에 걸칠 수 있다. 현재는 같은 결제를 여러 지출 행으로 나눠 기록하므로 나중에 카드 내역과 대조할 때 헷갈린다. 결제에 카드사 할인이 있으면 분류별 할인 배분도 직접 계산해야 한다.

이때 별도로 기록하는 할인은 카드사 할인이다. 상품 자체 할인은 이미 결제금액에 반영되어 있으므로 상품별 할인 배분 기능을 추가할 필요는 없다.

### 개선 요구

원래 결제 한 건을 유지하고 그 안에 분류별 세부 금액을 연결한다. 카드 내역 대조·실적·결제 준비는 원래 결제를 기준으로 처리하고, 지출 통계는 분류별 세부 금액을 합산한다. 분할된 내역을 별개의 실제 결제로 중복 집계하지 않는다.

카드사 할인은 분류별 할인 전 금액의 비율로 자동 배분하고, 원 단위 잔여액도 처리해 전체 합계를 일치시킨다.

| 분류      | 할인 전 금액 | 카드사 할인 배분 | 생활비 반영액 |
| --------- | ------------ | ---------------- | ------------- |
| 식품/외식 | 80,000원     | 4,000원          | 76,000원      |
| 생활/동물 | 20,000원     | 1,000원          | 19,000원      |
| 합계      | 100,000원    | 5,000원          | 95,000원      |

기본은 분류 하나이며 필요한 경우에만 나눈다. 잔여액 배분 순서와 부분 취소·할부·정산의 결합은 상세 계산 설계 대상이다.

## 18. 연말정산·절세 기능의 후속 확장 요구

### 기능 범위

연말정산·절세 기능은 MVP에서 제외하고 후속 확장이 가능한 거래 데이터를 유지한다.

### 데이터 설계 요구

- 원래 결제와 분류별 분할 내역을 연결하고 승인금액·카드사 할인·실제 부담액을 구분한다. 생활비용 순액만 남겨 원래 결제를 잃지 않는다.
- 결제수단 소유자, 실사용자, 비용 부담·정산, 공동생활비 귀속·공개 수준을 서로 다른 개념으로 유지한다. 어느 한 항목으로 세법상 귀속을 확정하지 않는다.
- 실제 거래의 날짜와 예산 반영 월을 구분하고, 예정 거래와 실제 거래의 관계를 추적할 수 있게 한다.
- 할부의 원거래·회차별 납부와 취소·환불의 관계를 보존할 방안을 설계한다. 생활비 차감 기준을 세무 집계 기준으로 그대로 재사용하지 않는다.
- 생활비 통계제외가 원거래 삭제나 모든 목적의 집계 제외를 뜻하지 않도록 한다. 대신 결제·용돈 사용 등도 필요한 거래 사실은 유지한다.
- 이미 저장한 거래를 추후 세무 분류·해당 연도 규칙과 연결할 수 있도록 확장 경계를 검토한다. 구체적인 세무 필드와 저장 구조는 아직 확정하지 않는다.
- 확정 거래와 필요한 출처 메타데이터를 유지하되 원본 파일·전체 셀 덤프·불필요한 개인정보는 보관하지 않는다.

공제 판정·세액 계산·절세 추천·세법 규칙 관리·입력 화면은 후속 범위다. 도입 시 해당 연도의 법령·귀속 기준을 적용한다.
