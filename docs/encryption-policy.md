# 금융 데이터 암호화·키 관리 규칙

작성일: 2026-11-04

적용 방식: KMS 봉투 암호화와 별도 세션 쿠키로 보호한 Redis 데이터 키 캐시. 원본 파일은 보관하지 않는다.

관련 문서: [제품 기획안](./product-plan.md), [스프레드시트 분석](./spreadsheet-analysis.md).

## 1. 보호 목표

- DB·백업·Redis 저장 내용의 유출과 운영자의 일상적인 직접 조회로부터 금융 상세를 보호한다.
- 서버에서 금융 데이터 처리·저장·동기화를 지원하며 여러 기기에서 사용할 수 있어야 한다.
- 복구키 보관·패스키 관리·기기 사전 등록을 사용자 필수 절차로 두지 않는다.
- 서버는 정상 처리 중 복호화할 수 있다. 운영자 단독 복호화 불가나 서버 전체 장악 방어는 보장 범위에서 제외한다.

## 2. 보호 대상

DB에 저장하는 모든 금액은 암호화한다. 거래금액뿐 아니라 수입, 잔액, 예산, 이월금, 할인·포인트의 금액, 준비금, 조정금, 받을 돈·정산금, 저장된 합계 등 파생 금액도 포함한다. 순액이나 합계만 평문으로 남기지 않는다.

설정 화면에 있다는 이유만으로 비민감 정보로 분류하지 않는다.

| 정보                                      | 분류 방향                                                     |
| ----------------------------------------- | ------------------------------------------------------------- |
| 테마·언어 등 일반 설정                    | 서버가 알아도 되는 운영 설정 후보                             |
| 예산 금액·개인 계좌 별칭·등록한 사람 이름 | 금융·개인 맥락을 드러내므로 민감 정보로 검토                  |
| 거래 사용처·메모·날짜·분류·실사용자       | 금액과 별개로 민감한 생활 정보를 드러낼 수 있음               |
| 파일·원본 셀·가져오기 자료                | 원본 파일은 보관하지 않으며, 처리 중 임시 자료도 종료 시 폐기 |
| 쿠키·토큰·평문 키                         | 접근 또는 복호화를 가능하게 하는 비밀정보                     |

구체적인 필드별 암호화·검색·인덱스 정책은 미정이다. 민감정보를 불필요하게 수집하지 않는 원칙을 유지한다.

### 원본 파일 비보관

- 업로드한 원본 파일을 DB·객체 저장소·백업·로그·오류 수집 자료로 보관하지 않는다.
- 가져오기와 사용자 확인에 필요한 동안만 일시 처리한다. 성공·실패·취소·만료 시 원본과 임시 사본을 폐기하며, 중단된 처리의 잔여 자료도 정리하도록 설계한다.
- 등록을 확정한 거래 데이터는 암호화해 저장한다. 원본 파일 전체나 원본 셀 덤프를 거래 데이터라는 이름으로 별도 보관하지 않는다.
- 원본 대조가 다시 필요하면 사용자가 파일을 다시 선택한다. 외부 AI 제공사의 입력 보관·삭제 정책은 도입 전 검증한다.

## 3. 공통 설계 규칙

- 직접 만든 암호 알고리즘을 사용하지 않는다. 검증된 라이브러리와 인증 암호화 방식을 사용한다. AES-GCM은 후보이며 nonce 재사용을 방지해야 한다.
- 키·세션 비밀값은 암호학적으로 안전한 난수로 생성한다. 사용자 ID·시간·짧은 PIN을 그대로 암호화 키로 쓰지 않는다.
- 평문 키를 소스, DB, Redis, 환경변수 등에 영구 저장하는 방식과 암호화된 키를 저장하는 방식을 구분한다. **암호화된 데이터 키는 DB에 저장할 수 있다.**
- 전송 구간, 저장 데이터·백업, 앱의 필드 암호화는 다른 계층이다. 저장장치 암호화만으로 DB 조회나 실행 중인 서버 접근까지 막는다고 설명하지 않는다.
- 캐시에 키가 있어도 매 요청의 인증·레코드 접근 권한을 검사한다. 캐시 적중이나 쿠키 보유만으로 다른 사람의 거래 접근을 허용하지 않는다.
- 실제 금융 상세·평문 키·인증 토큰·쿠키를 일반 로그, 오류 보고, 분석 이벤트, 테스트 자료에 남기지 않는다.
- 키 버전, 교체·폐기, 백업 복구, 접근 취소를 포함해 설계한다. 키 삭제로 실제 금융 기록을 복구 불가능하게 만들 수 있는 작업은 일반 캐시 정리와 구분한다.

## 4. KMS와 봉투 암호화

KMS가 데이터 키를 암복호화하고, 서버는 해제한 데이터 키로 금융 데이터를 처리한다.

| 구분                | 위치·역할                                                             |
| ------------------- | --------------------------------------------------------------------- |
| 최상위 키           | 관리형 KMS에서 데이터 키를 보호. 선택한 키 유형의 원문 반출 제한 확인 |
| 영구 데이터 키      | 암호화된 형태로 DB에 저장. KMS 권한을 가진 서버가 필요할 때 해제      |
| 금융 상세           | 데이터 키로 암호화해 DB에 저장                                        |
| 평문 데이터 키·상세 | 서버가 처리할 때 메모리에 일시 존재                                   |

KMS 제공사와 데이터 키의 사용자·가계부별 분리 단위는 상세 설계에서 정한다. KMS 상위 키와 금융 데이터를 암호화하는 데이터 키를 구분해 권한·비용을 산정한다.

운영자 계정과 운영 서버 신원을 구분하고, 키 관리와 키 사용 권한을 분리한다. 서버에는 필요한 범위의 키 사용 권한만 부여하는 방향을 검토한다. 모든 권한과 배포를 한 사람이 통제하면 의도적으로 권한·코드를 바꿔 접근할 가능성이 남는다.

이 방식은 서버 계산과 여러 기기 사용을 유지하고, 사용자에게 영구 복구키를 보관하게 하지 않는다. 대신 서버의 정상 복호화 능력은 유지되므로 운영자 접근 불가 또는 서버 전체 침해 방어를 보장하지 않는다.

KMS 권한·가용성·원래 키가 유지되어야 DB의 암호화된 데이터 키를 다시 열 수 있다. 관리형 서비스라는 이유만으로 모든 키 분실·삭제를 자동 복구한다고 가정하지 않는다.

## 5. 데이터 키 캐시

### 별도 쿠키로 암호화한 Redis 캐시

세션 식별용 쿠키와 별도로 안전한 난수를 만들고, 해당 비밀값으로 데이터 키를 암호화해 Redis에 임시 보관한다.

| 위치   | 내용                                                                         |
| ------ | ---------------------------------------------------------------------------- |
| 쿠키 A | 로그인 세션 식별자                                                           |
| 쿠키 B | 캐시 데이터 키를 암호화·복호화하는 세션 전용 비밀값                          |
| Redis  | 쿠키 B의 비밀값으로 암호화한 데이터 키, 검증·만료에 필요한 제한된 메타데이터 |
| DB     | 금융 암호문과 KMS로 보호한 영구 데이터 키                                    |

1. 인증·권한 확인 후 KMS로 필요한 데이터 키를 해제한다.
2. 세션 전용 비밀값으로 데이터 키를 암호화해 Redis에 저장하고, 비밀값은 쿠키 B로 전달한다.
3. 이후 요청에서는 세션·권한을 확인하고 쿠키 B로 Redis의 캐시 키를 해제해 처리한다.
4. 캐시가 만료되면 승인된 인증 흐름으로 영구 데이터 키를 KMS에서 다시 해제한다.

쿠키 B 비밀값을 Redis 세션, DB, 서버 설정·로그 등에 함께 저장하면 저장소 분리 효과가 없어진다. 세션 식별자도 가능하면 원문 대신 검증용 해시로 저장하는 방안을 검토한다. 새 기기·새 세션에는 새로운 세션 비밀값을 발급하며, 쿠키를 영구 데이터 키로 사용하지 않는다.

캐시 쿠키나 Redis가 없어져도 DB의 영구 데이터 키가 보존되므로 그것만으로 금융 기록이 유실되지는 않는다. KMS·인증 경로가 정상이라는 전제다.

### 세션·캐시의 조건

- 쿠키에는 HttpOnly·Secure·적절한 SameSite·범위를 적용하고 CSRF 방어를 별도로 검토한다. HttpOnly는 브라우저 JavaScript의 읽기를 제한할 뿐 서버 접근이나 요청 실행을 막지 않는다.
- 미사용 만료 외에 활동과 무관한 최대 수명을 둔다. 로그인 세션 수명과 데이터 키 캐시 수명을 동일하게 가정하지 않는다.
- 로그아웃·계정 잠금·권한 변경·키 교체 시 서버 측 세션 무효화와 캐시 사용 중단을 설계한다.
- 로그인·세션 교체·동시 요청·다중 기기·캐시 만료에서 잘못된 키를 연결하지 않도록 검증한다.
- 쿠키·요청 헤더·Set-Cookie·평문 키가 프록시·오류 수집·관측 도구에 기록되지 않도록 한다.
- Redis 접근 권한·TLS·백업·영속화·복제·진단 덤프를 검토한다. TTL 삭제가 과거 백업까지 지운다는 뜻은 아니다.

Redis에는 쿠키로 암호화한 키만 캐시한다. 복호화한 키는 요청 처리 중 서버 메모리에 일시 존재하며, 별도의 장기 평문 메모리 캐시를 기본 구성에 추가하지 않는다. 미사용 만료 시간·최대 수명·용량·무효화 방식의 구체적인 값은 구현 설계에서 정한다.

## 6. 공격자 접근 수준별 보호 범위

KMS 봉투 암호화·쿠키 기반 Redis 키 캐시의 보호 범위는 다음과 같다.

| 공격자가 확보한 접근            | 기대 효과와 한계                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| DB·백업 읽기                    | 키·KMS 권한·평문 사본이 함께 유출되지 않았다면 금융 암호문을 직접 해독하기 어렵게 함 |
| DB·Redis 저장 내용 읽기         | 쿠키 B 비밀값이 없으면 캐시 키도 직접 해제하기 어렵게 함                             |
| 서버 코드 실행·메모리·요청 접근 | 활성 요청의 쿠키, 해제된 키와 금융 상세를 가로챌 수 있음                             |
| 서버 신원으로 KMS 복호화 가능   | 허용된 영구 데이터 키를 해제하고 관련 과거 기록도 복호화할 수 있음                   |
| 개발자 계정의 일상적인 DB 조회  | 기본 권한에서 키 조회·KMS 사용을 분리해 직접 열람의 장벽을 높일 수 있음              |

서버 장악은 단순한 파일·설정 읽기와 코드 실행·메모리 접근을 구분해 평가한다. KMS 키 원문을 반출하지 못해도 KMS 복호화 권한을 악용하면 금융 데이터가 노출될 수 있다.

서버 코드 실행·요청·메모리와 해당 KMS 사용 권한을 모두 장악한 공격자는 금융 데이터에 접근할 수 있다.

## 7. 새 기기·세션 복구

- 인증 후 KMS로 영구 데이터 키를 해제하고 새 세션 비밀값으로 Redis 캐시를 구성한다.
- 쿠키·캐시 소실은 영구 데이터 키 소실과 구분한다. KMS와 DB의 암호화된 데이터 키가 유지되면 새 세션에서 금융 기록을 다시 사용할 수 있다.
- 카카오 사용자 ID·로그인 토큰은 영구 데이터 암호화 키로 사용하지 않는다.
- KMS 키·권한·암호화된 데이터 키의 유실과 장애는 별도 복구 절차가 필요하다.

## 8. 진단·지원

- 금융 원문·키·쿠키·토큰을 로그·오류 수집·분석 이벤트에 남기지 않는다.
- 오류 재현에는 합성 데이터를 사용한다.
- 진단 메타데이터의 수집 범위·권한·보관 기간과 사용자 자료 제공 절차는 상세 설계 대상이다.
- 운영자 예외 복호화·금융 상세 열람 절차는 별도 정책 승인 전까지 제공하지 않는다.

## 9. 구현 전 결정·검증 항목

1. 확정한 보호 목표인 직접 조회·저장소 유출 방어가 실제 권한·배포·로그 구성에서도 유지되는지 검증
2. 필드별 암호화 범위와 평문 메타데이터, 검색·합계·중복 대조 방식
3. KMS 제공사·키 단위·사용 권한·배포 신원·키 버전·교체·폐기·백업 복구
4. 채택한 쿠키 기반 Redis 캐시의 TTL·최대 수명·용량·무효화
5. 세션·캐시 키의 안전한 생성과 인증 암호화, nonce·사용자·세션·키 버전 결합
6. 다중 기기·공동 공유·구성원 권한 변경·캐시 소진에서의 접근 경계
7. 키 분실·KMS 장애·Redis 장애·세션 탈취·쿠키 변경·키 교체 시 실패 처리
8. AI·파일 가져오기·내보내기의 평문 처리 위치와 외부 전송·보관 범위
9. 진단 자료·사용자 동의·예외 접근 정책과 감사 기록의 비밀정보 제외
10. 실제 KMS 호출 수·캐시 적중률·지연·운영 비용과 새 기기 복구 테스트
